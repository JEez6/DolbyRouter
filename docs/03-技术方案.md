# 03 技术方案

## 1. 架构

```
┌───────────────────────────────────────────────────────────┐
│ com.dolbyrouter APK（仅配置 UI）                            │
│   • 勾选应用 → 写 /data/data/com.dolbyrouter/                │
│     shared_prefs/config.xml（镜像为 world-readable）         │
├───────────────────────────────────────────────────────────┤
│ DolbyRouter Zygisk 模块（zygisk/arm64-v8a.so）              │
│   • root companion：读上述 config.xml，按包名匹配            │
│   • preAppSpecialize：命中则在该进程内 inline hook          │
│      libaudioclient.so::AudioTrack::createTrack_l()         │
│      清 AUDIO_OUTPUT_FLAG_FAST|PRIMARY → 落普通轨 → 挂 DAP  │
│   • 可选 hook libaaudio_internal.so::AudioGlobal_           │
│      getMMapPolicy() 返回 0（NEVER），回落 legacy 路径       │
└───────────────────────────────────────────────────────────┘
```

不再使用 Xposed / LSPosed 作为注入路径（原 Java 层代码已删除）。

## 2. 配置模型

存储文件（UI 端）：`/data/data/com.dolbyrouter/shared_prefs/config.xml`
（世界可读；MIUI 会把 SharedPreferences 重定向，故 `PrefsHelper.persist()` 用文件 IO 显式镜像回标准路径）

| Key | 类型 | 含义 |
| --- | --- | --- |
| `enabled_global` | bool | 模块总开关 |
| `scope_<pkg>` | bool | 该应用纳入处理范围 = 强制走普通混音链（挂杜比） |

native 侧 companion 每收到一次 `preAppSpecialize` 请求就重读该文件（无需重启应用即可改配置）。

**手动覆盖**：模块目录下的扁平文件 `/data/adb/modules/dolbyrouter/perapp.conf`
（`enabled=1` + 每行 `app=<pkg>`），用于无 UI 时手工调试；与 `config.xml` 是 **OR** 关系。

**二值语义**（见旧 F 节决策）：命中 = `force_normal`（strip_fast + block_mmap 都开）；未命中 = 放行。

## 3. 收口点：为什么是 createTrack_l

- 只清 `createTrack_l()` 入口的 `mFlags`（清 `FAST 0x4` 与 `PRIMARY 0x2`）。
- **不**在 `set()` / 构造函数层动任何入参。原因是 OpenSL 的 `notificationFrames = -numBuffers`
  是 FAST-only 契约，在 set 层清 FAST 会破坏 refill 节奏，导致卡顿/慢放（见 [02](02-音频栈与Dolby机制.md) 3.2）。
- `createTrack_l` 位于 `mFlags` 已由 `set()` 完整建立、即将发给 AudioFlinger 之前，是唯一既能去 FAST
  又不改语义的时点，且被三条 API 共用。

| Hook 目标 | 库 | 动作 |
| --- | --- | --- |
| `AudioTrack::createTrack_l()` | `libaudioclient.so` | `mFlags(this+0x378) &= ~(FAST\|PRIMARY)` |
| `AudioGlobal_getMMapPolicy()` | `libaaudio_internal.so` | 返回 0（NEVER），回落 legacy AudioTrack |

- `mFlags` 偏移 `0x378` 与符号名均已对设备 `/system/lib64/libaudioclient.so` 反汇编核对。
- inline hook 框架：**shadowhook**（bytedance/android-inline-hook，静态编入模块）。
  shadowhook 处于 `MODE_UNIQUE`，目标直接跳 proxy，**不能**用 `SHADOWHOOK_CALL_PREV`（会崩），直接调用保存的 `orig` 指针。
- 打包的 shadowhook 源码有一处修改：`sh_linker_init()` 直接 `return 0`（原实现依赖 `dlopen("libshadowhook_nothing.so")`
  做握手，在 Zygisk Next 注入环境下失败，导致 init errno=12）。该 linker 拦截仅用于 dl_init 回调，本模块不使用。

## 4. 已知限制

- **实时低延迟 OpenSL 游戏**（如喵斯快跑 `com.prpr.musedash.TapTap`）：其 OpenSL BufferQueue 依赖 FAST 轨道
  的 notification/RT 时序，强制转普通轨会出现慢放/卡顿。当前**不支持**，需在名单外放行。
- MMAP/独占路径：AAudio 通过 getMMapPolicy=NEVER 回落；若未来有应用绕过该符号，需另找收口点。
- 目标应用需为 arm64-v8a（模块只带 arm64 库）。

## 5. UI 设计

- **MainActivity**：总开关、已选应用列表（点条目可「移出范围」）。
- **AppPickerActivity**：勾选应用（应用名 + 包名，系统应用加 `[系统]` 前缀并排最后），带搜索框。
- 应用枚举用 `queryIntentActivities(MAIN+LAUNCHER)` 绕过 MIUI 对 `QUERY_ALL_PACKAGES` 的限制（见 04）。

## 6. 风险与回退

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 强制普通轨导致音画不同步/卡顿 | 部分实时应用体验下降 | per-app 粒度；出问题从名单移除 |
| hook 崩溃目标应用 | 应用闪退 | 关闭总开关、或删除模块目录后重启 |
| 清 PRIMARY 影响路由 | 个别轨道落点异常 | 收口点仅改目标进程 |
| shadowhook linker 修改 | 版本升级后行为变化 | 已记录；升级时重新评估 |
